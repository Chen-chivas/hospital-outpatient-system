# 项目结构与模块划分（基于需求分析）

本文档根据仓库中的需求分析文档，给出可落地的**项目目录结构**与**模块边界**，用于后续详细设计与实现。

涉及的需求文档（仓库根目录原件）：

- `第4组-2023112544-张靖雅-需求分析.docx`：就诊管理、药房管理、收费管理（含AI辅助诊断与医保接口描述）
- `第四组-2023112416-陈锦涛-需求分析.docx`：挂号管理（多渠道预约、分时段号源、排班、退改签、停诊、黑名单、并发号源管控）
- `第四组-2013112463-王颖-需求分析.docx`：用户管理、数据统计与分析（趋势/维度/导出/看板等）

> 说明：三份文档对应不同成员负责模块。项目结构按“共享基础能力 + 业务模块”整合。

---

## 1. 总体架构建议

需求文档反复出现以下特征：多角色操作（医生/护士/收费员/药师/管理员/患者）、跨模块数据流转（挂号→就诊→收费→发药）、统计报表与可视化、与 HIS/LIS/PACS/医保 等外部系统对接预留、并发与安全要求。

因此推荐：

- **前后端分离（B/S）**：前端负责交互与可视化，后端提供统一 REST API。
- **后端模块化单体（Modular Monolith）**：先用一个后端服务承载所有模块，按包/目录隔离边界；课程项目更易联调与部署。
- **为外部对接留“适配层（integration）”**：HIS/LIS/PACS/医保接口先以 stub/mock 形式实现，避免阻塞主流程。

后续如果需要扩展为微服务，可把各业务模块从单体拆分为独立服务（目录结构已按模块可拆分设计）。

### 1.1 语言与技术栈（当前落地）

当前仓库按 **Java（Spring Boot）后端 + Vue 前端** 的思路落地目录与模块边界，优先保证“前后端分离 + 模块化后端”的结构清晰，便于团队协作与后续扩展。

## 3. 业务模块划分（与需求映射）

### 3.1 用户与权限（user/auth/audit）

来自：`第四组-2013112463-王颖-需求分析.docx` + `第四组-2023112416-陈锦涛-需求分析.docx`（实名核验/挂号资格校验）。

建议拆成 3 个子模块：

- `auth`：登录鉴权、token 会话、密码策略、接口鉴权中间件
- `user`：人员与账号（患者/医生/护士/收费员/药师/管理员），账号状态（启用/禁用/黑名单），实名信息
- `audit`：操作日志、打印日志等不可篡改审计数据（至少做到“追加写”）

### 3.2 挂号管理（registration）

来自：`第四组-2023112416-陈锦涛-需求分析.docx`。

核心域对象建议：

- 排班：`Schedule`（医生、日期、时段、号种）
- 号源：`Slot`（时段号源池、可预约/锁定/已预约/下架）
- 挂号订单：`RegistrationOrder`（渠道、费用、状态、流水号）
- 停诊：`StopClinicRequest`（申请、审核、通知、下架号源）
- 退改签：`Refund/Reschedule`（规则校验、退费）
- 黑名单：`NoShow/Blacklist`（爽约累计与限制策略）

### 3.3 就诊管理（visit/emr）

来自：`第4组-2023112544-张靖雅-需求分析.docx`（电子病历、AI辅助诊断、处方流转等）。

建议包含：

- 就诊接诊：挂号订单核验、接诊开始/结束
- 电子病历（EMR）：主诉、现病史、体征、诊断、处置
- 检查检验申请（可先做结构预留）：对接 LIS/PACS 的请求与结果回填
- AI辅助诊断：对外部模型服务的调用与结果落库（先 stub/mock）

### 3.4 药房管理（pharmacy/inventory/dispense）

来自：`第4组-2023112544-张靖雅-需求分析.docx`。

建议包含：

- 处方审核/调配/发药：状态流转、复核、发药记录
- 库存管理：入库/出库/盘点/报损/效期预警/库存预警
- 药品字典：规格、批号、监管码、效期等

### 3.5 收费管理（billing/payment/insurance/invoice）

来自：`第4组-2023112544-张靖雅-需求分析.docx` + `第四组-2023112416-陈锦涛-需求分析.docx`（挂号支付、退费）。

建议包含：

- 费用计算：项目、药品、检查、治疗等费用明细与合计
- 支付/退费：挂号支付、退号退费，状态机与幂等
- 医保结算（预留）：医保中心接口调用、超时/异常的手工录入/重试机制
- 发票/单据：打印模板与打印日志

### 3.6 数据统计与分析（statistics/report/export/dashboard）

来自：`第四组-2013112463-王颖-需求分析.docx`。

建议包含：

- 指标统计：门诊量/挂号数/就诊人数/处方数/缴费人次、营收汇总、均值、占比
- 维度分析：时间/科室/医生/患者/费用维度
- 趋势对比：环比/同比/排行/波动
- 可视化：折线/柱状/饼图/热力图/数字看板
- 导出：Excel/PDF（后端生成或前端导出均可，先预留服务层）

## 4. 后端目录结构（建议，面向模块化实现）

以下以“单个后端服务 + 按模块分包”为主（便于课程项目落地）。

```
backend/
├─ README.md
└─ src/
   ├─ main/
   │  ├─ java/
   │  │  └─ <base-package>/
   │  │     ├─ common/                # 通用：异常、返回体、分页、校验等
   │  │     ├─ security/              # 鉴权、RBAC、脱敏/加密、接口权限拦截
   │  │     ├─ integration/           # HIS/LIS/PACS/医保/AI模型等适配层
   │  │     ├─ module/
   │  │     │  ├─ user/               # 用户、角色、权限、实名信息
   │  │     │  ├─ audit/              # 操作日志、打印日志
   │  │     │  ├─ registration/       # 挂号、排班、号源、停诊、退改签
   │  │     │  ├─ visit/              # 接诊、病历、诊断、处方开立
   │  │     │  ├─ pharmacy/           # 处方审核/调配/发药、库存
   │  │     │  ├─ billing/            # 费用、支付、退费、医保结算预留
   │  │     │  └─ statistics/         # 统计查询、报表、导出
   │  │     └─ Application.java
   │  └─ resources/
   │     ├─ application.yml
   │     └─ db/                       # 可选：迁移脚本（Flyway/Liquibase）
   └─ test/
      └─ java/
```

每个业务模块内部再按分层组织（推荐固定约定，降低协作成本）：

```
module/<name>/
├─ api/            # controller + request/response DTO
├─ application/    # service 编排（用例层）
├─ domain/         # 领域对象、领域服务、状态机/规则
└─ infra/          # repository、mapper、外部调用、缓存、锁
```

> 如果团队更熟悉传统三层，也可以统一使用 `controller/service/repository/entity/dto`；关键是**模块边界清晰**。

## 5. 前端目录结构（建议，按业务模块拆分）

```
frontend/
├─ README.md
└─ src/
   ├─ api/                   # 按模块封装请求：user.ts、registration.ts...
   ├─ router/                # 路由与权限守卫（基于角色/权限）
   ├─ store/                 # 全局状态（用户信息、权限、字典等）
   ├─ views/
   │  ├─ login/
   │  ├─ user/
   │  ├─ registration/
   │  ├─ visit/
   │  ├─ pharmacy/
   │  ├─ billing/
   │  └─ statistics/
   ├─ components/            # 通用组件（表格、导出、图表等）
   └─ utils/                 # 权限、格式化、脱敏展示等
```

统计与可视化建议单独沉淀：

- `components/charts/`：折线/柱状/饼图/热力图组件
- `views/statistics/dashboard`：数字看板与趋势图

## 6. 数据库目录结构（建议）

```
database/
├─ README.md
├─ schema/
│  ├─ 001_init.sql            # 建表（或按模块拆分）
│  └─ 002_seed.sql            # 初始化数据：角色、权限、字典
└─ diagrams/                  # 可选：ER图、数据字典
```

按需求的核心表大致可按模块拆分（便于协作）：

- `user_*`：用户/角色/权限/账号状态
- `registration_*`：排班/号源/挂号订单/退改签/停诊/黑名单
- `visit_*`：就诊记录/病历/诊断/医嘱/处方
- `pharmacy_*`：药品字典/库存/出入库/发药记录/处方审核
- `billing_*`：费用明细/支付/退费/发票/医保结算记录
- `stat_*`：可不单独建表，优先用聚合查询；必要时建“指标快照表”
- `audit_*`：操作日志/打印日志（建议只追加写）

## 7. 关键横切能力（必须在结构中预留）

这些能力来自三份文档的非功能需求与接口要求，建议作为独立目录/模块存在：

- **权限分级与菜单控制**：后端权限点 + 前端路由守卫
- **日志与审计**：操作留痕、不可篡改（至少逻辑只追加）
- **敏感信息保护**：身份证/手机号加密存储、脱敏展示
- **幂等与状态机**：支付/退费/退号/发药等必须可重试、不重复扣减
- **对接适配层**：HIS/LIS/PACS/医保/AI模型接口，便于 mock 与替换
- **导出与打印**：Excel/PDF 导出、打印模板与打印日志
